# How it works

The daemon in the order it runs. Text in backticks is the script's own: a knob, a command, or a log line quoted as printed. `N`, `X` and `ID` stand for a number, a network name and a network id; `IF` stands for the interface name. Story lines are quoted in English; with `LOG_LANG=ar` the local log carries the program's Arabic text instead, and `DEBUG` lines stay English.

## Start-up

`awacs.sh` with no argument is the daemon; `check` and `help` run without root, everything else needs root. `/etc/awacs.conf` is sourced when it is owned by root and neither group nor others can read or write it (mode `0600` is the script's own advice); every knob is validated and falls back to its default when malformed ([configuration.md](configuration.md)), and `LOG_TARGET` `both` or `remote` without `SITE_URL` is downgraded to `local`. A refused or missing file and the knobs that fell back are said once in the log after the `reporting:` line: `settings file /etc/awacs.conf ignored: mode 644, chmod 600 it - running on built-in defaults (no site, no emergency networks)`, `settings file /etc/awacs.conf ignored: not owned by root, chown root: it - running on built-in defaults (no site, no emergency networks)`, `settings file /etc/awacs.conf not found - running on built-in defaults (no site, no emergency networks)`, `settings file /etc/awacs.conf applied, but 2 values failed validation and use their defaults: TICK, SITE_TZ` (names, never values). The interface is `AWACS_IF`, else the best of `iw dev` (connected, then up, then present), else `wlan0`. `/run/awacs` holds the lock, the scan cache, the spool, the temporary-network marker and the site-command files (`cmd`, `cmd.ready`, `cmd.last`, `cmd.answer`, `join_id`); a second daemon fails the lock and exits; without a terminal it says so once per boot, `another AWACS already holds the lock (pid N) - two launchers are running it, keep one (the rc.local line or the systemd unit)`, into the shared spool that the running daemon's next flush delivers.

The backend is `wpa` when NetworkManager is neither active nor enabled, `nm` when it is, and `nm_lame` when NetworkManager is present but `nmcli` is missing or the interface is unmanaged; a start waits up to 60 s for NetworkManager to become active first. Under `nm` any call into `wpa_cli` is logged as `BUG: wpa_cli reached under nm backend: ...`.

The first log line is `AWACS 1.0 starting on wlan0 (device mydevice) - wpa backend, first start of this boot, up 1 min` (`NetworkManager backend` on nm; `restart N of this boot` when a launcher brought the daemon back in the same boot, counted in `/run/awacs/starts`; the uptime reads `45 s`, `3 min`, `2 h 15 min` or `3 d 4 h`). When the previous daemon ordered the reboot the device just came out of, `starting after the reboot AWACS ordered at 2026-01-01 03:41 - wedged 30 min (HomeNet, OfficeNet on the air but this device cannot join), 7 recovery runs before it` follows at once (see [The reboot condition](#the-reboot-condition)). Then the local confirmation `reporting: both -> https://example.org | probe: https://example.org/mydevice/receiver.php | wifi cell: auto | lang: local <en|ar>, site <en|ar>` (`reporting: local | probe: none - signal mode | wifi cell: auto | lang: local <en|ar>, site <en|ar>` without a site); the settings verdict and the fallen knobs when there are any; `wifi cell asked for (REPORT_WIFI=yes) but SITE_URL is empty - nothing to publish to` when that pair is set; `time zone Asia/Kuwaitt is unknown on this device (no such zone) - stamps fall back to UTC` when an `Area/City` zone has no file under `/usr/share/zoneinfo` (`tzdata not installed` when the whole tree is missing); `device id not usable (DEVICE_ID: my camera) - reporting as cam1` when a present id fails the slug rule; and the summary of the working settings, `running with: measured mode, floor 400/200 kbps day/night (night 22:00-06:00), switch gain 150%, one evaluation per 20 min, reboot after 30 min wedged, wifi cell on, 3 stored networks, 0 emergency, open networks yes, stamps in the device zone` (`running with: signal mode (no probe target - networks chosen by signal), reboot after 30 min wedged, wifi cell off (no SITE_URL), 3 stored networks, 0 emergency, open networks yes, stamps in the device zone` without a probe target; `floor 400 kbps (night profile off)` with the night profile off; the cell part reads `on`, `off (REPORT_WIFI=no)`, `off (no SITE_URL)` or `off (auto with LOG_TARGET local)`; the emergency figure is a count, never a name; no address appears). A missing interface logs `interface wlan0 not present - is the WiFi hardware alive?`, a missing tool `missing tools: ... - will try to install once online`, the nm backend `NetworkManager backend - AWACS supervises it (full capability)`. Then `rfkill list wifi` is read and `rfkill unblock wifi` runs (on nm also `nmcli radio wifi on`): a radio found soft-blocked says `wifi radio was soft-blocked at start - unblocked (a WLAN country not set, or a saved rfkill state)`, a hard-blocked one `wifi radio is hard-blocked - a hardware switch, AWACS cannot unblock it`, an open radio nothing. Then power save off; `stealth mode active (icmp hidden, avahi stopped)` when `STEALTH_MODE` is `yes` and both legs succeeded, else `stealth mode partly active: iptables missing - pings still answered` (the parts, comma-joined, are `iptables missing - pings still answered`, `ping rule could not be added - pings still answered` and `avahi could not be stopped`); removal of a temporary network left by a previous daemon, said as `removed the temporary network FreeCafe left by the previous run` (a WARN ending `- the device was still on it, recovery follows` when the device still rode it); `enable_all` (every stored network re-enabled: `enable_network all` on wpa, `nmcli -w 5 device connect IF` on nm when the device is disconnected or failed) and on wpa `arm_hidden` (`scan_ssid 1` on every stored network in the live supplicant). Before that, a join the previous daemon did not finish is removed through `/run/awacs/join_id`, `removed an unfinished join of CafeNet left by the previous run`; after it, every network in `/etc/awacs.networks` whose SSID has no profile yet is re-added, `re-added 1 networks joined from the site: CafeNet`. The device key `/etc/awacs.key` is made at the first start that finds `openssl` (`device key made for passwords typed on the site (/etc/awacs.key)`) and offered to the site, `device key registered with the site - a password typed there can be opened here` on the first 2xx of the boot (again at the third healthy tick, then once a healthy minute until it is accepted); a 403 is `the site holds another key for this camera (a reflash?) - open admin/wifi.php?reset_key=1 once from your phone, then join from the menu works again`, once per boot. The `SIGUSR1` trap for site commands is installed before the backend is detected, so no daemon path runs untrapped, and `/run/awacs/cmd.ready` is created once the lock is won, so the site's relay signals only a daemon that can take the signal. With internet the spool is flushed and `online at start via HomeNet` follows; without it `no internet at start on HomeNet - router still answers, engaging` (`router silent too` when associated with a silent gateway, `router none (not associated)` without an association) and recovery starts before the first tick; its win is said by `internet restored` on the first healthy tick like any other.

## Stopping and unexpected exits

On SIGTERM, SIGINT, SIGQUIT or SIGHUP the daemon re-enables every stored network and says `AWACS stopping on SIGTERM (systemctl stop or shutdown) - stored networks re-enabled, the network layer runs on its own until the next start` (`SIGINT (Ctrl+C)`, `SIGHUP (terminal closed)` or `SIGQUIT` in place of the first part). The line is sent in the foreground before the exit, so it reaches the site under systemd too, and no restart is claimed. The stop also drains the spool, bounded to 6 lines or 20 s so it ends inside the unit's `TimeoutStopSec=40`; the rest waits for the successor's start flush, and the local file notes `stop drain reached its budget - the remaining held lines wait for the next start`. An exit nobody ordered (an unbound variable under `set -u`, a failed `exec`, a stray `exit`) is caught by an EXIT trap: `AWACS exited unexpectedly (status 1, last command in fight: echo "$UNBOUND_THING") - the launcher restarts it in 10 s` (`- no launcher under -d, start it again` when started with `-d`). The command is the unexpanded source text, so no secret travels, and the function is named when the exit happened inside one. The line is sent in the foreground; when the site is unreachable it waits in the spool and the successor's start flush delivers it. Both lines are silent for the reboot the daemon orders itself. Every start counts itself in `/run/awacs/starts`, so the successor's start line reads `restart N of this boot`.

## The tick

The wait between ticks is `sleep TICK` run in the background and awaited, so a `SIGUSR1` from the site's relay ends it at once; the flag it sets is read right after the clock check below and nowhere else (see [Site commands](#site-commands)). Every `TICK` seconds the daemon compares the wall clock with the uptime clock (a difference of more than 60 s since the previous tick is a time-sync step, said once as `clock set forward 7 h 0 min by time sync - the lines above carry the old time`, or `back 2 min`), applies the day or night profile (`night profile active until 06:00 - floor 200 kbps, a challenger must reach 300% of the incumbent, evaluations 40 min apart` or `day profile active until 22:00 - floor 400 kbps, a challenger must reach 150% of the incumbent, evaluations 20 min apart`, logged on a transition only; the gain is phrased as a share of the incumbent because the bar is the incumbent's measurement times the gain divided by 100) and runs the internet check; the first passing rung means online:

1. `ping -c 1 -W 2 8.8.8.8`
2. `ping -c 1 -W 2 1.1.1.1`
3. HTTP 204 from `http://connectivitycheck.gstatic.com/generate_204`, 3 s limit
4. HTTP 400 from `${SITE_URL}/${DEVICE_ID}/${SITE_API}` for a POST carrying `probe=1`, 3 s limit; only when `SITE_URL` is set

Both HTTP rungs compare the exact status code, so a captive portal's 200 or 302 reads as offline; a link where ping works but DNS does not reads as online.

The same four steps also run in a patient form, used only where a busy link would otherwise be misread: three pings per target 0.3 s apart with a 5 s wait each, and an 8 s limit on both HTTP steps. Every tick starts with the quick form above, and the toolbox words `check` and `status` use that form only.

A failed quick check is not a failure by itself. The daemon reads the interface's `tx_bytes` counter before and after the check: 16384 bytes or more sent while the check was failing means the device was busy sending (an upload, a live stream), and one patient check then decides the tick. A link that sent less than that counts as failed at once, so a dead link keeps its old timing. The patient check is paid at most once per outage: after one has failed, every following tick is decided by the quick check alone, and any passing quick check clears that state. With `DEBUG=yes` the two outcomes are `quick check timed out under load (sent ${sent} B during it) - patient check passed` and `sent ${sent} B during the failed quick check, the patient check failed too - counting it`.

A healthy tick clears the failure counter and the reboot timer, logs `internet restored: X - down 5 min, 3 recovery runs` after a recovery (the duration from the loss line, `run` for one run; every step a recovery repeated in the outage follows as `repeated N more times during the outage (last at HH:MM): ...`), flushes the spool (third healthy tick in a row, then every thirtieth) and says what it delivered (see [The spool](#the-spool)), runs the once-per-boot tool install, sends the WiFi cell every six ticks (checking the device id first: `device id changed: cam1 -> cam2 - reporting under cam2 from now` when it changed), removes a temporary network once the device sits on another network (`back on a stored network: HomeNet - temporary network FreeCafe removed`), and runs the passive upload meter and the preferred-network return. On the tick that reaches `NET_FAIL_TICKS` one more test comes first, on two conditions: the link itself is alive (the default gateway answers a ping, or the kernel's neighbour table lists it `REACHABLE`) and no patient check has failed in this outage yet. That test is a patient check. When it passes, the tick counts as healthy, no recovery starts, and the local file carries `internet answers late, not never - slow link, no recovery (${NET_FAIL_TICKS} quick checks timed out)`; that line is never sent to the site. The site gets the episode instead: `uplink answering late on HomeNet - 3 quick checks timed out, the patient check passed, no recovery` at the first late pass; `internet answered late N more times in the last hour on HomeNet - slow link, no recovery` at most once an hour while late passes continue; `uplink answers normally again on HomeNet - answered late N times over 26 min` after 30 quick passes in a row (about 5 min). A new episode opens no sooner than 30 min after that closer, and late passes inside the quiet window are folded into the next one. A loss that ends an open episode says `internet answered late N more times before this loss on HomeNet - slow link` before its loss line. Otherwise the daemon pings the gateway once more and logs `internet lost on HomeNet - router still answers, engaging` once (`router silent too` when associated with a silent gateway, `router none (not associated)` when the association is gone) and runs a recovery on this and every following tick until the internet is back. With the defaults, a link whose gateway has gone silent engages 40 to 63 s after the loss, and an upstream outage on a link whose router keeps answering engages about 72 to 83 s after it; the difference is that one patient check.

## Recovery

A recovery returns as soon as the internet is verified. It checks that the interface still exists (`interface wlan0 has vanished - WiFi hardware or driver gone, rung L3 reloads the driver (a USB dongle needs replugging)`, once per outage, when an interface seen alive earlier in this run is gone), removes the daemon's own temporary network (`dropping temporary network FreeCafe - it stopped delivering`, once per outage), runs `enable_all` and `arm_hidden`, then reads the link. With a gateway that answers, the first recovery of an outage keeps the association: it skips the reassociate, remembers the network the device is on as the one to come back to, and only waits; with `DEBUG=yes` the skip is logged as `gentle open skipped: the link is alive (gateway reachable) - the outage is upstream`. The second recovery of the same outage reassociates anyway, because a router that answers a ping yet forwards nothing for this device is cured by a fresh association. With a dead link it reassociates at once (`wpa_cli reassociate`; on nm `nmcli -w 5 device connect IF` when the device is disconnected or failed). The opening is said once per outage per variant: `router answers on HomeNet - keeping the link, trying the other stored networks first`; on wpa the second recovery says `router answers on HomeNet but forwards nothing - reassociating anyway this time`; a dead link says `router not answering - waiting up to 25 s for wlan0 to reconnect`. Either way it waits up to `ASSOC_WAIT` seconds for an IPv4 lease. Asking for the network the device already rides with an address never re-activates it: that network is proven where it stands, so a live association is not bounced. If the internet check still fails, three rounds follow. In each:

1. nm only: wait for NetworkManager to settle; a passing internet check ends the recovery. A device in a connecting state (40 to 90) or deactivating (110) logs `NM is still trying - waiting it out`: no stored network is tried, the round takes the external branch and the reboot timer is cleared.
2. Every visible stored network is tried and measured (below); a working one ends the recovery. The first walk of an outage names the air first, `scan heard 4 networks: HomeNet -48, OfficeNet -61, Cafe -70, Guest -74 | known on the air: HomeNet, OfficeNet | stored, not heard: none`, said again only when the set of visible stored networks changes and counted otherwise. When the link was alive at the start of the recovery, the remembered network is left out of that list and is the one the device is put back on when no other network delivered.
3. The outage is classified as on the device or external (next section), before any temporary network is attached, because attaching and detaching one drops the route and the association and would make every external outage look like a fault on the device.
4. On the device: `fault looks on the device: HomeNet, OfficeNet on the air but this device cannot join - recovery follows` (the sign is one of `... on the air but this device cannot join`, `the radio hears no network at all`, `the stored network list cannot be read` and `the stored network list reads empty`; said once per outage per sign, and the wrong-password line takes its place when that sign is present), then the rung of this round (L1, L2, L3), the internet check, then the emergency networks, then the open networks. External: the verdict names its reason, `outage looks external: the router answers, the fault is upstream (round N) — waiting, not rebooting`, `outage looks external: OfficeNet linked but no internet, the fault is behind that network (round N) — waiting, not rebooting`, `outage looks external: none of your 2 stored networks is on the air, 4 others heard (round N) — waiting, not rebooting`, or `outage looks external (round N) — waiting, not rebooting` when NetworkManager was busy at the start of the round; each is said once per outage and counted on later rounds; the reboot timer is cleared, the emergency and open networks are tried, and the round ends with a 20 s pause. A failed emergency or open attempt is followed by re-enabling every stored network, and on the external branch by a return to the remembered network, so no round runs its pause with the device parked on a stranger or with its stored networks left disabled. A way back that fails is said once per outage, `could not return to HomeNet: never associated - stored networks re-enabled, waiting 20 s` (not when the link formed without internet, which is the external outage itself).

After three losing rounds the reboot condition is evaluated; if it is not met, `enable_all` runs, the recovery returns failure and the next tick starts another.

### Recovery rungs

| Rung | wpa backend | nm backend |
| --- | --- | --- |
| L1 | `recover L1: radio bounce`: `rfkill unblock wifi`, `ip link set IF down`, 2 s, `up`, 3 s | `recover L1: radio bounce`: block and unblock the interface's own rfkill index, or `nmcli radio wifi off` and `on` without one; wait up to 15 s for NetworkManager to settle |
| L2 | `recover L2: restart dhcpcd (respawns the REAL per-interface supplicant)`: `systemctl restart dhcpcd` (else `wpa_supplicant`), 8 s, `arm_hidden`, power save off | `recover L2: re-kick NetworkManager on wlan0`: `nmcli device reapply IF`, 3 s; if still offline `nmcli device disconnect IF`, 1 s, `nmcli -w 5 device connect IF`, 8 s; power save off |
| L3 | `recover L3: reload brcmfmac firmware (the 3-second cure a wedge needs)`: `modprobe -r brcmfmac`, 2 s, `modprobe brcmfmac`, 8 s, `arm_hidden`, power save off | `recover L3: restart NetworkManager + reload WiFi firmware`: `systemctl restart NetworkManager`, 8 s, the same `brcmfmac` reload, every `awacs-*` keyfile under `/run/NetworkManager/system-connections` removed, `nmcli connection reload` |

`brcmfmac` is the driver of the Raspberry Pi WiFi chip; on other hardware the reload does nothing. On nm the daemon never runs `ip link set down` or `up` and never restarts `dhcpcd`. The rung lines of both backends are said once per outage and counted on later recoveries. A rung whose load-bearing command failed says so, once per outage: `recover L1 did not complete: wlan0 would not come back up - radio not bounced` (wpa), `recover L2 did not complete: dhcpcd and wpa_supplicant both refused to restart - supplicant not respawned` (wpa), `recover L3 did not complete: brcmfmac would not unload - firmware not reloaded` (both backends, only where the driver was loaded) and `recover L3 did not complete: NetworkManager refused to restart - firmware reload follows` (nm; said before the firmware step, which runs anyway).

### Emergency and open networks

Emergency networks are the `SAFETY_NET` entries of the conf, names with passwords (an empty password lists an open hotspot). With a non-empty list the daemon logs `trying emergency networks (N listed)` and tries each entry whether or not the scan shows it, since a hotspot is often switched on a moment ago or hidden; success is `connected to EMERGENCY network: X (upload N kbps) - stored networks stay armed, home again when one returns` (`(signal mode)` in place of the figure without a probe target; the figure is one probe on the new network). Every entry's fate is said once per outage per entry, names only. On wpa an entry whose name contains a backslash or a double quote, or whose password contains a double quote, is skipped with `emergency network X skipped: name or password carries a quote or backslash the supplicant cannot take`; on nm a non-empty password must be 8 to 63 characters or 64 hex digits, else `emergency network X skipped: password must be 8-63 characters or 64 hex digits`. An entry the supplicant or NetworkManager would not create is `could not create the temporary entry for X - skipping it`; a tried entry that failed is `emergency network X refused: never associated - trying the next` (the reasons are those of the candidate walk); the walk closes with `no emergency network delivered (N tried, M skipped)`.

Open networks come last and only when `OPEN_NETWORKS` is `yes`: `trying open networks as last resort (N open networks heard)` (once per outage), then every open network the scan shows, skipping signals below -80 dBm (wpa) or 25 % (nm) and, on wpa, non-ASCII names. A network that links but forwards nothing is `open network X linked but no internet (captive portal?) - trying the next` (once per outage per network; a stranger that refuses the association is counted, not said); the walk closes with `no open network delivered internet (N heard, M tried, K linked without internet)`; success is `connected to OPEN network: X (upload N kbps) - stored networks stay armed, home again when one returns`.

Both are temporary entries, on wpa in the live supplicant, on nm a keyfile under `/run/NetworkManager/system-connections` named `awacs-safety-*` or `awacs-crutch-*` with `autoconnect=false`; the id is recorded in `/run/awacs/open_id` so that a crashed daemon's successor removes it. The entry is removed at the next recovery start (`dropping temporary network X - it stopped delivering`), on a healthy tick once the device sits on another network (`back on a stored network: HomeNet - temporary network X removed`), by rung L3 on nm, and at every daemon start (`removed the temporary network X left by the previous run`, a WARN ending `- the device was still on it, recovery follows` when the device still rode it). Nothing is written to `wpa_supplicant.conf` or `/etc/NetworkManager`.

## On-device fault versus external outage

A round is a fault on the device only when all of these hold: NetworkManager is not in a connecting state this round (nm); no default gateway on the interface answers a ping; no association with an IPv4 lease succeeded this round; and at least one sign is present: a stored network is visible yet could not be joined, the scan shows nothing at all, or the stored network list is empty. Anything else is external: a gateway that answers means the link works and the fault is upstream.

Inside the on-device branch a wrong password takes precedence. Its sign is a `TEMP-DISABLED` entry in `list_networks` on wpa, or on nm an activation error mentioning secrets or authentication, remembered for the rest of the recovery. The line names the refusing networks, `association refused by HomeNet - wrong password? (recovery continues, reboot stays off)` (the `TEMP-DISABLED` rows on wpa, the refused profile on nm; `association refused - wrong password? (recovery continues, reboot stays off)` when no name is known), said once per outage per set of names; the rungs still run, because a stale hotspot password can coincide with a real fault, and the reboot timer is set to zero every time the sign is seen. With `DEBUG=yes` each on-device round also writes `fight round N: ME evidence (LINK_OK=0, gw unreachable, auth_failing=N)`, the last `N` being 1 when the wrong-password sign was seen and 0 otherwise.

On nm one more read follows: the daemon waits for NetworkManager to settle and checks the internet again. A device back in a connecting state logs `NM is still trying - waiting it out` and the round ends after 20 s with no rung. A device in state 100 (connected) without internet means the fault is behind the router: `NetworkManager is connected, internet is not (round N) — router-side, no rung`; the timer is cleared, the emergency and open networks are tried, and the round ends after 20 s. An `nmcli` that exits 8 means NetworkManager itself is not answering: `NetworkManager is not answering nmcli (exit 8) - stored networks cannot be tried until it is restarted (recover L3)`, said at the first exit 8 of a streak; while it lasts the on-device sign reads `the stored network list cannot be read` and a candidate's reason `NetworkManager not answering`.

## The reboot condition

The reboot timer records the first on-device classification of the current streak. On wpa it is set directly. On nm it is set only when NetworkManager has given up: device state 30 or 120 on two consecutive classifications with no connecting state seen between them, or an unreadable state while `nmcli` itself fails (exit 8) after rung L3 has already restarted NetworkManager; state 20 (unavailable) never sets it. The timer is cleared by a healthy tick, any successful connect, an external classification, the wrong-password sign, and on nm by any connecting-state sighting or any readable state other than 30 or 120. The first arming in an outage is said, `reboot clock armed - the device reboots after 03:41 unless the internet returns or the fault reads external` (the hour is the deadline in `SITE_TZ`; the valve fires at the end of the first losing recovery after it); re-arming in the same outage is counted. On nm the two clears that had no line of their own (a connecting or readable state after an arming) say `reboot clock cleared - NetworkManager picked the device up again` once; the other clears keep their own lines.

At the end of a losing recovery, when the timer has been set for `REBOOT_AFTER_MIN` minutes (and on nm NetworkManager is still given up), the daemon writes `rebooting now: wedged 30 min (HomeNet, OfficeNet on the air but this device cannot join) - reboot 1 for this fault, the story continues after the boot` (the sign is the one that holds at that moment: `... on the air but this device cannot join`, `the radio hears no network at all` or `the stored network list reads empty`; the count numbers the reboots of this fault and is kept in `/var/log/awacs.log.reboots` until a healthy tick), saves its memory beside the log, runs `sync`, waits 2 s and reboots. After the reboot the timer starts from zero.

The memory is what lets the story survive the reboot. `/run` is tmpfs, and the spool, which holds the whole outage since the network went down, would die with it. So the daemon copies the spool, the line above included, to `/var/log/awacs.log.spool` and writes a marker, `/var/log/awacs.log.reboot`, with the time, the number of recovery runs, the boot id and the sign. The next start reads the marker first. A different boot id means the reboot happened: the saved copy is put in front of the spool, the marker and the copy are removed, and right after the start line the daemon says `starting after the reboot AWACS ordered at 2026-01-01 03:41 - wedged 30 min (HomeNet, OfficeNet on the air but this device cannot join), 7 recovery runs before it`; the start's flush then delivers, in order, the outage story, the reboot line, the start line and that WARN. A power cut leaves no marker, so a start after one reads plain. The same boot id means the `reboot` command did not run (a respawn in the same boot found the marker, or the daemon that issued the command is still alive): after 60 s alive it says `the reboot AWACS ordered at 2026-01-01 03:41 did not happen - the reboot command failed, check the device` and drops the marker and the copy; the 60 s keep a normal shutdown from being misread. No reboot happens for a wrong password, for an external outage, while NetworkManager is still trying, or while any network delivers internet. `REBOOT_AFTER_MIN` cannot be 0; the validator falls back to 30.

## NetworkManager supervision

On nm the daemon intervenes only after `NET_FAIL_TICKS` failing ticks and only once the device has left its connecting and deactivating states, waiting up to `ASSOC_WAIT` seconds for that. Stored profiles are joined with `nmcli connection up` by uuid. It never runs `nmcli device wifi connect`, which writes a profile to `/etc`, never `nmcli connection modify`, and downs or deletes a profile only when its name is `awacs-crutch-*`, `awacs-safety-*`, `awacs-join-*` or `awacs-joined-*` and its file lies under `/run/NetworkManager/system-connections`; anything else is refused with `REFUSING delete: 'name' is not an awacs profile` or `REFUSING delete: 'name' lives outside /run (owner file?)`.

In `nm_lame` the verdict names the reason and the cure: `NetworkManager image but AWACS cannot drive it: nmcli is missing - will install it once online and restart - monitoring only` (under `-d`: `NetworkManager image but AWACS cannot drive it: nmcli is missing - will install it once online, then restart AWACS by hand (started with -d) - monitoring only`), or `NetworkManager image but AWACS cannot drive it: wlan0 is unmanaged by NetworkManager - fix unmanaged-devices in NetworkManager.conf and restart AWACS - monitoring only`. The daemon then checks the internet every 300 s, flushes the spool and lets the tool install run once; a change of verdict is said once each way, `internet lost on HomeNet - monitoring only, AWACS cannot recover here` and `internet back on HomeNet - monitoring only` (the spool is flushed before the second, so the site reads the pair in order). When a missing `nmcli` was the reason and the install brought it, the daemon logs `nmcli is now installed - restarting as a full NetworkManager supervisor` and exits so that systemd or the `rc.local` loop restarts it (a `-d` start has no launcher and stays).

## Upload measurement and the switch rule

One measurement is one upload of `PROBE_KB` KB to `PROBE_URL`, else the endpoint, with `curl --data-binary`, 15 s limit; when curl reports 0 and `wget` exists the same upload is timed with `wget --post-file`. The result is in kbps. A probe the target refused (no byte accepted, with curl and with the wget fallback) is said as `upload probe failed on HomeNet - the probe target accepted nothing (site or endpoint down?), counting it as 0 kbps` in place of the measured line, and counts as 0.

A comparison walks the visible stored networks except the current one: `trying X`, connect (a failure is `could not connect to X: REASON - trying the next`, the reason being `never associated`, `associated but got no address`, `refused - wrong password?`, `not found on the air`, `timed out after 25 s`, `NetworkManager not answering`, `NetworkManager: <its own message>` or `linked but no internet`; `no association or no address` is the fallback), measure, log `candidate [ID] X uploads at N kbps` (or the probe-failed line), keep the fastest, stop early when a candidate reaches four times the profile floor. The winner is announced and joined: `switching to X (N kbps against M kbps here)` inside an evaluation, `switching to X (N kbps, the fastest candidate)` inside a recovery, with ` - plainly fast, over 4x the F kbps floor, probing stopped at it` appended when the early stop ended the walk, then `switched to X (upload N kbps)`. A switch that fails is `switching to X failed: REASON - going back to Y`, followed by `back on Y` or `could not return to Y: REASON`; in a recovery, where there is no network to go back to, the line ends at the reason. Inside a recovery the floor is 0, so any working network beats none. Inside an evaluation the floor is the current network's measured speed times `SWITCH_GAIN_PCT` (`NIGHT_GAIN_PCT` at night) divided by 100; when nobody beats it the daemon goes back and says what happened: `no challenger beat the incumbent - staying on X (best was Y at N kbps, needed B)` when candidates were measured, `the only candidate did not deliver internet - staying on X at N kbps` or `none of the T candidates delivered internet - staying on X at N kbps` when none was, `no other known network on the air - staying on X at N kbps` when there was nobody to try (inside a recovery the same lines end at the name). A way home that links without internet is `back on X - linked but still no internet, recovery continues` inside a recovery and `back on X - linked but still no internet` outside one; a way home that fails is `could not return to X: REASON`; both once per outage per network and reason. The best candidate is then joined anyway, `switching to Y (N kbps, below the B kbps bar) - the best left, X: REASON` in an evaluation and `switching to Y (N kbps) - it delivered internet, X: REASON` in a recovery. An evaluation that ends with neither a switch nor a way home says `evaluation ended with no working network - on Z now, the next check decides and recovery follows if the internet is gone` (`nothing` when the device sits on no network).

An evaluation is triggered by the passive meter: each healthy tick samples the interface's `tx_bytes` counter for 3 s. A flow between 20 kbps and the profile floor (`MIN_UP_KBPS` by day, `NIGHT_MIN_UP_KBPS` at night) is a strike; any sample outside that band, an idle one below 20 kbps included, resets the strikes to zero. After `UP_STRIKES` strikes and at least `DANCE_COOLDOWN` (`NIGHT_DANCE_COOLDOWN`) seconds since the last evaluation, the daemon logs `sustained slow upload on X (N kbps for 3 samples, floor 400) - evaluating known networks`, names what the radio hears (`scan heard N networks: X -45, Y -60, ... | known on the air: X, ... | stored, not heard: Z, ...`, strongest first, at most ten names in each part, `none` for an empty part), measures the current network once (`measured N kbps on X - under the 400 kbps floor, a challenger must beat B kbps`), and starts the comparison only when that measurement is under the floor; otherwise the measured line reads `measured N kbps on X - above the 400 kbps floor, staying`. Strikes that are ripe while the cooldown still runs are said once per cooldown window, `upload still slow on X (N kbps, floor 400) - evaluation on cooldown, next look in 12 min`. While a live stream runs (`raspistill` with `live_raw`, `preview.jpg` or `capture.jpg` on its command line, or `curl` with `upfile=@`; other workloads are not detected) the band is 5 kbps to `STREAM_MIN_KBPS` and the lines are `live stream starving on X (N kbps for 3 samples, floor 50) - evaluating known networks` and, under the cooldown, `live stream still starving on X (N kbps, floor 50) - evaluation on cooldown, next look in 12 min`; a stream above `STREAM_MIN_KBPS` is never interrupted.

## Preferred-network return

Every `PREF_CHECK` seconds, unless a stream runs, the daemon looks for a visible stored network whose priority is strictly higher than the current one's (wpa `priority`, nm `connection.autoconnect-priority`); on wpa a supplicant-side scan runs first so that hidden networks are seen. After two consecutive sightings: `higher-priority network X visible twice - leaving Y to go home` (with ` (seen and lost N times before)` appended when the candidate flickered during this stay), a connect (a failure is `could not reach the preferred network X: REASON - going back to Y`, or `... - no stored network to go back to, the next check decides` when the network the device left is not known), and a measurement on arrival, `measured N kbps on X`. Under the floor means `preferred network X too slow (N kbps, floor 400) - benched for 60 min, going back to Y` (`- benched for 60 min, staying on it` with nothing to go back to; `, ends the bench on Z` appended when another network's bench was still running; the minutes are three cooldowns): the candidate is ignored for that long and the previous network is rejoined, `back on Y`. A way back that links without internet is `back on Y - linked but still no internet`; a way back that fails is `could not return to Y: REASON` followed by `the way back to Y failed - on Z now, the next check decides` (`no network` when the device sits on none). Otherwise `returned to preferred network: X (upload N kbps)`. A candidate seen at one look and gone at the next is `preferred network X was visible at one check and gone at the next - staying on Y until it holds for two checks in a row`, once per stay on the current network; later flickers are counted into the attempt line. A manual switch from the site onto a stored network of lower priority changes none of this: the next `PREF_CHECK` looks treat it like any other stay, and after the same two sightings the daemon goes back to the higher-priority network as it always did, so a manual trial never overrides the stored priorities.

## Signal mode

Without `SITE_URL` and without `PROBE_URL` there is nothing to upload to; the reporting line says `probe: none - signal mode` and the start summary `running with: signal mode (no probe target - networks chosen by signal), ...`; an emergency or open network that delivers reads `(signal mode)` in place of the upload figure. A comparison then walks the visible stored networks strongest first (`trying X`, and `could not connect to X: REASON - trying the next` on a failure) and keeps the first one that delivers internet: `connected: X (signal mode - no upload probe target configured)`. The passive meter counts no strikes, so no evaluation starts, and the preferred-network return does not measure on arrival: `returned to preferred network: X (signal mode)`. `awacs.sh speed` reports that no probe target is configured. Everything else, the internet check's first three rungs included, is unchanged.

## The spool

Every reported event goes to `/var/log/awacs.log` in the language `LOG_LANG` selects (with `LOG_TARGET=remote` only `WARN` and `ERROR`). With `SITE_URL` set and `LOG_TARGET` `both` or `remote`, a site copy `yyyy-mm-ddThh:mm:ss+hh:mm [LEVEL][awacs] message` is built in the language `SITE_LANG` selects (a line with no Arabic text stays English) and POSTed in the background as `file=log/log.txt` with a 4 s limit; when the POST fails, or while offline, the copy is appended to `/run/awacs/spool`. Above `SPOOL_CAP` lines, line 1 is kept and the newest `SPOOL_CAP - 1` lines follow it: the first line of an outage carries the time it began, so the middle of the story is what is dropped. A flush sends line by line, stops at the first failure and keeps the remainder in front of any new lines.

What happens to the story is said too. A site that answers a live line with anything outside 2xx and 3xx, or not within 4 s, while the internet is up opens an episode: `site did not take the log line (http 500) - holding lines, delivery retried about every 5 min` (`no reply in 4 s` for a timeout; the minutes are 30 ticks), said once and held behind the refused line; later refusals are silent until the held lines go out. Every flush that delivered lines says so after them, in the foreground (a start whose spool held only its own start lines says nothing): `delivered 9 held lines stamped 03:10 to 03:41 - they stand above this line with their own times` (`delivered 1 held line stamped 03:10 - it stands above this line with its own time` for one); when the flush ends a refusal episode and everything held went out, the line is `site reachable again - delivered 9 held lines stamped 03:10 to 03:41, they stand above this line with their own times`. Lines the cap dropped are counted in `/run/awacs/spool.dropped` and said once the story is out in full: `outage story trimmed - 14 lines dropped from its middle (the spool keeps 60)`. The WiFi cell has its own episode, `wifi cell not accepted by the site (http 403) - the page drops the cell when it goes stale` and `wifi cell accepted again`; the scan list too, `wifi scan list not accepted by the site (http 500) - the list behind the WiFi box will not show` and `wifi scan list accepted again`; the local file has its own, `local log /var/log/awacs.log not writable - SD card read-only? the site keeps the story` and `local log /var/log/awacs.log writable again`, said on the first healthy tick after the change. Before a reboot the daemon orders itself the spool is copied beside the log and restored at the next start (see [The reboot condition](#the-reboot-condition)). The counts that follow `internet restored` name the last repeat: `repeated 12 more times during the outage (last at 03:41): ...`.

## Scanning and the deaf-radio rule

A scan lists every visible network strongest first and is cached in `/run/awacs/scan` for `SCAN_TTL` seconds. Sources, in order: `iw dev IF scan` (up to 3 tries 3 s apart, 6 within the first 180 s of uptime; one wait on `Device or resource busy`, since the supplicant or NetworkManager is scanning and its own table holds the answer), then `iwlist IF scan`, then that table (`wpa_cli scan_results`, or NetworkManager's list with `--rescan no`).

When every source is empty the daemon logs `scan failed - using previous results (if any)`, serves the old cache and refreshes its timestamp, so a silent radio is asked once per `SCAN_TTL`. Three such scans in a row mean the radio hears nothing: `radio heard nothing on 3 scans in a row - previous results dropped`, logged once, and the cache becomes an empty answer; from then on the scan-shows-nothing sign holds for classification and the reboot condition can be met on a dead radio. Any scan that hears a beacon, even a hidden one, ends the streak. Scans run by the toolbox words log these warnings locally only.

## Site commands

A site with a WiFi menu asks for a scan, a `switch` (a trial of a stored network) or a `join` (a trial of a new network with a password typed on the site). Its relay on the device writes one line to `/run/awacs/cmd`, `<uptime_seconds>\t<epoch>\t<cmd>\t<key>\t<blob>` (the key is the SSID as lowercase hex from the scan list's sixth column; the blob is the encrypted password, join only), and sends `SIGUSR1` to the PID in the lock while `/run/awacs/cmd.ready` exists. The daemon consumes the file at one point, the top of the main loop after the clock check: it deletes it before acting, so a crash cannot replay it; ignores a repeat of the same epoch (`/run/awacs/cmd.last`); answers `failed expired` when the line is older than 60 s by uptime (`site command scan expired - it waited 2 min behind a recovery, tap again`), `failed busy` while a recovery is engaged (`site command switch refused - a recovery is running, tap again when the internet is back`) and `failed offline` while the internet is down; and otherwise answers `taken` and runs the command. Nothing about a command runs inside `fight()` or an evaluation. Every answer, `<answer_epoch>\t<cmd_epoch>\t<state>\t<field>...`, is kept in `/run/awacs/cmd.answer`, posted in the foreground as `file=tmp/wifi_state.tmp` and re-sent on every healthy tick until the site takes it. From the tap on the site to `taken` the path is about one to three seconds: the signal itself ends the sleep within a fraction of a second, the rest is the site's own hold and one HTTP round trip.

Scan: on wpa the cache is dropped and `scan` runs; on nm `nmcli device wifi rescan` then NetworkManager's list. The publish gate is lifted, the list is posted in the foreground, `scan from the site heard 7 networks - list published`, and the answer is `done N`. Under a live stream `scan asked from the site under a live stream - a few seconds of stutter` precedes it.

Switch and join share one trial. The origin is remembered (`current_id`, its name, its last measured upload when under 120 s old, else one probe now), the opening line names the bar, `manual trial: OfficeNet for 15 s, leaving HomeNet (1200 kbps) - it stays only at 1800 kbps or more` (the bar is the origin's upload times `SWITCH_GAIN_PCT`, or the night gain, divided by 100), and `connect_id` runs on the target. When the link forms and the internet is verified the answer is `trying NAME` and the cell is republished; otherwise the daemon goes back to the origin at once, `manual trial: OfficeNet never associated - going back to HomeNet` (WARN, with the connect verdict), and answers `failed` with the verdict's token: `refused - wrong password?` is `wrong_password`, `linked but no internet` is `no_internet`, anything else `out_of_reach`. The `TRIAL_WAIT` window (15 s) opens the moment the internet is verified; the `trying` answer stands alone for `TRIAL_HEAD` (5 s) so the site's polls see it, then the one probe of the trial starts inside the window and its start is the answer `measuring NAME`; the verdict comes at the later of the window and the head plus the probe, so on the owner's links the network is held for the 15 s and the probe's seconds add nothing to them. The network stays only when its upload is above zero and at least the bar (in signal mode, any network that delivered stays), `manual trial: OfficeNet upload 2000 kbps, the 1800 kbps bar met - staying on it` and the answer `switched` or `joined`; otherwise `manual trial: OfficeNet uploads at 700 kbps, under the 1800 kbps bar (HomeNet 1200 kbps at 150%) - going back`, `return_to` the origin, `back on HomeNet`, and the answer `returned ORIGIN OKBPS TRIAL TKBPS`. A way back that links without internet counts as returned (the device is home; the outage is upstream); one that forms no link is `the way back to HomeNet failed - on no network now, the next check decides and recovery follows if the internet is gone` and `failed return_failed`. `enable_all` runs on every exit, the trial counts as an evaluation for `DANCE_COOLDOWN`, and neither the evaluation nor `fight()` is ever called from it.

Join adds the password step in front. The blob is `<iv_hex>.<ct_base64>.<mac_hex>`; the daemon derives `Kenc` and `Kmac` from `/etc/awacs.key` with HMAC-SHA256, checks the MAC over the ASCII text `<iv_hex>.<ct_base64>` before touching the ciphertext, then decrypts with `openssl enc -d -aes-256-cbc`; a MAC that does not verify is `join asked from the site for CafeNet - the password could not be opened with this device's key; the site holds another key? open admin/wifi.php?reset_key=1 once and try again`, the key is offered to the site again, and the answer is `failed key_changed`. A password outside 8 to 63 characters (or 64 hex digits), or carrying a tab or newline, is refused as `wrong_password`. Then `join asked from the site: CafeNet - adding it at runtime and trying it for 15 s`: on wpa `add_network`, `set_network ID ssid <hex>`, the psk over stdin (a quote or backslash in a passphrase is refused first: the supplicant cannot take it), `scan_ssid 1`, `enable_network`, never `save_config`; on nm a keyfile in `/run` named `awacs-join-<epoch>-<pid>` with autoconnect off, never `nmcli device wifi connect`. `/run/awacs/join_id` marks the attempt. A connect that fails removes the entry, `join: CafeNet refused - wrong password? - removing it, going back to HomeNet`, and forgets the password. A link that delivers internet proves the password: it goes to `/etc/awacs.networks` first (`joined CafeNet - password kept in /etc/awacs.networks, re-added at every start`), the marker is removed, on nm the persistent `awacs-joined-<hexssid>` (autoconnect on) is created and connected and the trial entry deleted, the scan list is republished so the row turns known, and the 15 s trial decides `joined` or `returned`; the password is kept either way. `/etc/awacs.networks` is read again at every start and after the rungs that restart the supplicant (wpa L2 and L3) or NetworkManager (nm L3), `re-added 1 networks joined from the site: CafeNet`. The deletion guard on nm accepts these two beside the crutch and safety classes, and nothing else; the reaps skip `awacs-joined-*`; the reaps skip `awacs-joined-*`.

Two consequences of a site without a login are stated, not solved: the relay's long poll is a plain GET, so whoever fetches it first consumes a pending command, like a shutter press on such a site; and the key registration is pinned but open, so one who reaches the endpoint before the device ever registers holds the key the site will use, which the device reports as the 403 line at every start. The derived keys pass through `openssl`'s argument list for the call's duration on this single-user root device; the password never does.

## Network names

On wpa, matching uses the escaped text both `iw` and `wpa_cli` print (`\xNN` for non-ASCII bytes); on nm, the lowercase hex of the SSID bytes. Display decodes both; hex is never displayed. The two wpa-only name limits are listed in [faq.md](faq.md).
